# 四角い地球 大型版: 確認済みの事実 (2026-10-16 時点)

試行錯誤の経緯は含めない。確かめた事実だけを書く。経緯は `../WIRING.md` と `../tmp/` (非公開) にある。

## 構成

| 部品 | 型番 | 備考 |
|---|---|---|
| コントローラー | Seeed XIAO ESP32-S3 (Sense 無し、PSRAM 8MB) | MAC `68:EE:8F:4B:1E:84` |
| 表示コントローラー基板 | ER-PCBA5981-1 (Levetop LT7680A-R、SDRAM 内蔵) | 4 線 SPI で制御。目視で LT7680A-R を確認 |
| パネル | ER-TFT040-3 (4 インチ 480x480 IPS、ST7701S) | RGB は基板から、初期化は 3 線 SPI を XIAO から直接 |
| 電源 | XIAO の USB-C から 5V | 基板の VDD は 5V |

配線 (CON1 の番号 = 1mm 20 ピン変換基板の番号):

| CON1 | 信号 | XIAO |
|---|---|---|
| 1, 2 | GND | GND |
| 3, 4 | VDD | 5V |
| 5 | LCM_SCS | D0 |
| 6 | LCM_SDO | D9 (MISO) |
| 7 | LCM_SDI | D10 (MOSI) |
| 8 | LCM_SCLK | D8 (SCK) |
| 9 | BL_CONTROL | D3 |
| 11 | LCM_RESET | D1 (open drain + 内蔵プルアップ) |
| 16 | LCD_CS | D2 |
| 18 | LCD_DIN | D5 |
| 19 | LCD_SCLK | D4 |

基板について確かめたこと:

- LCM_RESET には基板上のプルアップが無い。XIAO 側で open drain + 内蔵プルアップにして High に保つ
- バックライトは出荷時 (J1 短絡) で外部信号 BL_CONTROL により点灯する
- LCD_DIN は書き込み専用で、パネルからの読み出しはできない
- パネルの RST は CON1 に出ていない。基板上の RC リセット (R9 10kΩ で基板の 3.3V へ、C27 1µF で GND へ、時定数 10ms) だけにつながっており、マイコンからは操作できない (メーカー回答、2026-10-16)
- メーカー推奨の電源投入手順は「電源投入後 20〜30ms 待って RC リセットの完了を待ち、それから ST7701S を初期化する」

## 動いているもの

### LT7680 (`lt7680_*`)

- SPI: モード 3 (0 と 2 も可、1 は不可)。1 語 16 クロック、先頭 8 ビットが 0x00 = レジスタ番号、0x80 = データ書き込み、0x40 = 状態読み出し、0xC0 = データ読み出し
- PLL と SDRAM の初期化、480x480 の表示タイミング設定、レジスタの書き込みと読み返し
- カラーバー、BTE の四角形塗りつぶし、前景色の設定
- 表示用メモリへの画素の書き込み (REG[04h] の memory data port に RGB565 リトルエンディアンを 64 バイトずつ) と読み返しの一致確認
- 480x480 の全面書き込みは、画素のバーストが SPI 1 MHz で約 4.1 秒、10 MHz で 776 ms (レジスタの読み書きは 1 MHz のまま、`-DPIXEL_SPI_HZ=10000000`)。10 MHz で地球の書き込みと白塗りを 10 回繰り返し、10 回とも正しく映った (LCD_CS をつないだ状態)
- 20 MHz では 588 ms。10 回繰り返して 10 回とも映った。全画素の読み返し (`#V`、1 MHz、約 15 秒) で照合すると、1、10、20 MHz のどれで書いても 23 万画素のうち 6〜8 画素で 1 ビットが 0 から 1 に化けていて、速さによる差は無い
- 読み返すたびに化けた画素が増える (2 回目で約 20〜40)。何も読まずに 90 秒置いても増えない (7 画素)。読み返しそのものが表示用メモリを乱している。読み返さない普段の使い方では、時間がたっても絵は崩れない
- LT7680 側は接続が確定してから一度も失敗していない

### パネル (ST7701S)

- 初期化はメーカーのデモ (`LCD_init.h`) の列を 3 線 9 ビット SPI でビットバンして送る (CS は 1 語ごと、CLK Low でデータを置き High で取り込ませる)
- 初期化用の LCD_DIN と LCD_SCLK は LT7680 の SPI と相乗りさせない (相乗りすると真っ黒のまま)
- 正常に映っている状態では、反転 (INVON/INVOFF)、ソフトリセット、初期化列の再送が効く

### 地球の描画 (`lt7680_earth`)

- NASA Blue Marble (2002) から QSC (Quadrilateralized Spherical Cube) の 1 面を 480x480 の RGB565 に変換し (`make_qsc_faces.py`、pyproj の `+proj=qsc`)、ヘッダ `earth_qsc480.h` として焼き込む
- 起動直後と、シリアル命令 `#E` の両方で、地球の面 (日本からオーストラリア) がパネルに映ることをカメラで確認した

### 山頂型モジュール 2 個で 6 面 (`lt7680_multi`、hub3)

- 1 モジュール = XIAO ESP32-S3 Sense + hub3 + LT7680 基板 3 枚。基板 0, 1, 2 が `#N` の A, B, C
- モジュール 1 (B8:F8:62:F8:DB:A0): 辺 A2:B1 B2:C1 C2:A1。A = 面 3 (アフリカ) 回転 0、B = 面 0 (日本) 回転 1、C = 面 4 (北極) 回転 2 (2026-10-29 の 4 度目の並び、ESP-NOW で割り当て)
- モジュール 2 (8C:BF:EA:8F:3F:38): 辺 A2:B1 B2:C1 C2:A1。A = 面 5 (南極) 回転 3、B = 面 2 回転 2、C = 面 1 回転 3 (2026-10-29 の 2 度目の並び)
- `#I` (リセットを掛けずに選んだ基板だけ初期化し直す) のあと、その基板に緑の筋が出て、描き直しても残った (2026-10-29、両モジュールで)。ESP-NOW で `#A` (LCM_RESET を全基板に掛けて初期化し直す) を送り、`#E` で描き直すと消えた。閉じた立方体の電源を抜かずに直せる
- 同じ日、閉じた立方体のモジュール 1 の基板 A だけ、`#A` のあとも画素 SPI 20MHz で描くと緑の筋が残った。`#S5` (5MHz) で描き直すと消えた (本人の目視)。このときは四角いモバイルバッテリーで動いていた。同じ夜、pi4-deck の USB 給電で再起動すると、20MHz のまま 3 面とも安定し、`#G` も 30fps (1 コマ 19.8ms、TIMEOUT 無し) で回った (本人の目視とシリアル)。このときは電源の電圧が下がっていたせいと読んだが、誤りだった。原因は SCK と MOSI の出力の強さ (`SPI_DRIVE` 1) で、出力 3 にすると四角いモバイルバッテリーでも崩れない (下の 2026-11-03 の項)
- モジュール 2 を丸いモバイルバッテリー (2500mAh) で動かすと、`#G` の描き換えが止まった (2026-10-29 に 2 回。止まっている間もマイコンは `#G` を最後まで回し、終わってから ESP-NOW の ping を返した)。pi5-deck の USB 給電に替えると問題なく動いた (本人の目視)。このときは丸い電池の 5V が負荷に追いつかないと読んだが、根拠が無くなった。2026-11-03 に、出力 1 のままでは AC アダプターでも崩れ、出力 3 では電池でも崩れなかった (下の項)。出力 1 の化けは回ごとに出たり出なかったりするので、1 回ずつの電源の比較で取り違えたと読んでいる。丸い電池は出力 3 ではまだ試していない
- 2 個を合わせて、境目で海岸線がつながる立方体の地球になることを目で確認した (2026-10-29)
- 電源は、四角いモバイルバッテリー (MARKLESS STYLE TE-0012、2000mAh、61 x 61 x 14 mm、USB-C ケーブル内蔵) を 2 個にして、両モジュールに 1 個ずつ。2 個とも立方体の中に収まり、蓋も閉まる (2026-11-03、本人)。SPI の出力を 3 にしてからは、これで `#G` を 10 分回しても崩れない (上の項)。持ち時間は、連続で描き換えて約 1 時間 29 分 (10/29 に 1 個で測った値、出力 1 のとき)
- 3 台 (2 モジュールと母艦の中継 68:EE:8F:4B:1E:84) とも、起動時に `secrets.h` の AP (自宅の pi5-w-1、外ではスマホのテザリング) に同じ並びでつなぎ、ESP-NOW はその AP のチャンネル (pi5-w-1 なら 6) に乗る。起動から Wi-Fi まで約 8 秒 (2026-11-03)
- `#j` で Web の JPEG を描ける: `https://z.yuiseki.net/static/tmp/cubic-earth/<名前>-side-a〜c.jpg` (母艦の `/sata_hdd_24tb/www/html/static/tmp/cubic-earth/`)。名前は `#m` で NVS に (モジュール 1 = north、2 = south)。1 枚 15KB で、取るのに約 0.65 秒 (HTTPS)、展開 47ms、描くのに 0.59 秒。6 面とも、画像の上がパネルの上で描かれ、north-side-b が北極、south-side-b が南極の面になった (本人の目視、2026-11-03)
- `#t` で本物の飛行機の 1 日を動かせる: adsb.lol の globe_history (ODbL) の 2026-11-03 から、定期便を 15 分ごとに取り、洋上の途切れは大円で補い (`flights/globe_snapshots.py --fill`)、どの時点でも 1 面 60 機まで選んだ 4,890 便、1.9MB (`flights/pack_flights.py`)。`#J` で Web から取って microSD に書き、PSRAM に読む (取得 10〜13 秒、読み込み 1.2〜2.0 秒)。`#t30` は南極側 1 コマ 57ms (18 コマ/秒)、北極側 62ms (16 コマ/秒)、レジスタの化けは両方 0 回。両モジュールとも本人の目視で「良い感じ」(2026-11-04)。書き込みで merged.bin を 0x0 に書くと NVS の面の割り当てと名前が消える (南極側で面がずれた)。アプリだけを 0x10000 に書けば残る (北極側で確認)
- `#t` で本物の船も動く: aisstream.io を毎時 5 分受けた 2026-11-04 の 13 時間分から、連続 2 時間に写った船を 1 面 30 隻まで選んだ 566 隻、58KB (`flights/collect_ais.py`、`flights/daily_ships.py`)。`#J` で flights.bin と一緒に取れた (0.9 秒)。南極側で飛行機と合わせて 5,456 個、1 コマ 64.0ms (16 コマ/秒)、レジスタの化け 0 回。白い点が見えた。北極側は 1 コマ 70.2ms (14 コマ/秒)、化け 0 回で、喜望峰に船が集まって見えた (本人の目視)。組んだキューブに ESP-NOW の中継から `#b1` と `#t130` を両モジュールへ同時に送り、6 面とも動いて面の境目もつながった (本人の目視、2026-11-05)。船は 1 日 120 秒の再生で 1 秒 0.3 画素しか動かず、飛行機と比べるとほぼ止まって見えるが、速さの比のとおりなのでそのままにする (本人の判断、2026-11-05)
- `#t` の飛行機と船を 11x11 の絵にした (`lt7680_multi/icons.h`)。飛行機は進む向きへ 8 方向に回し、船は船底がその場所の南を向くように 90 度ずつ回す。1 コマは南極側 72.4ms (14 コマ/秒)、北極側 81.3ms (12 コマ/秒)、化け 0 回。両面とも飛行機も船も正しく見えた (本人の目視、2026-11-05)
- 毎日 10:10 の `ais-ships-daily` が 2026-11-04 の 14 時間分から 603 隻、62,728 バイトの ships.bin を出し、組んだキューブに中継から `#J` を送ると両モジュールが取りに来た (nginx のログ、2026-11-05 10:37)
- 何もしないときにバックライトを消す `#i<分>` (USB ホストがいるときだけ): モジュール 1 を pi4-deck につないで `#i1` にすると、命令の 1 分後に消えた (シリアル)。消える前は pi4-deck の電池が 42% (3.55V) から 13% (3.39V) まで沈み、消したあと戻り始めた。モバイルバッテリーにつなぎ替えると、`#i1` のままでも 2 分以上消えなかった (2026-11-03、本人の目視)。設定は既定の 10 分に戻した
- `#G` (飛行機と船) を続けると面が崩れたのは、電源ではなく SCK と MOSI の出力の強さ (`SPI_DRIVE`、`#H<0-3>`) だった (2026-11-03、モジュール 2)
  - 崩れ方: 砂嵐、斜めの帯、スプライトの置き場 (赤紫の地に黄色の文字) が映る、ラベルの地が透明にならず赤紫で出る、基板の BTE が返事をしなくなり 1 回 100ms 待たされてほかの面も止まる。描き直す (`#A` と `#E`) と戻る
  - 電源では説明できない: モバイルバッテリー、PC の USB、AC アダプターのどれでも崩れ、XIAO の USB-C の入口は 4.76〜4.94V、0.79〜0.87A で崩れの前後も動かなかった。バックライトを消しても崩れた
  - `#G` の間に 1 秒ごと各基板のレジスタを読み返して (`reg_verify.h`)、化けを数えた。チップの中の値が化けていた (2 回読んで同じ)。例: 基板 0 の REG[D7h] (透明色) が F8 でなく D5 や 6A、基板 1 の REG[97h] (BTE の写し元の幅) が E0 でなく 10 (BTE を始める REG[90h] に書く値)。アドレスとデータがずれて別のレジスタに入っているように見える
  - 化けた基板は回ごとに違った (基板 0 だけ、基板 0 と 1、など)。面の割り当てを入れ替えると、崩れは面でなく基板についてきた
  - レジスタ 10MHz、`#A` で初期化してから `#G30` の比較: 出力 0 は 3 枚とも全滅 (VSYNC と BTE のタイムアウトばかり)、出力 1 (既定) は 1 秒〜数秒で 1〜2 枚が化け BTE が止まる (3 回とも)、出力 3 は 0 回。出力 3 のまま `#G90` で 0 回、今朝崩れた条件 (`#G60` と `#p` を約 70 秒おき) で 10 分、549 回読み返して 3 枚とも 0 回、タイムアウト 0 回、1 コマ 14ms。本人も「かつてないくらい安定」と目視
  - 出力 1 のままレジスタを 1MHz に下げると、30 秒で化けは読み出しの 1 回だけ (チップの中は正しい) だった。速さを落とすと軽くなるが、出力 3 なら 10MHz でよい
  - 10/28 には、基板 0 の画素 20MHz で出力 2 が化け、1 と 3 は 0 画素だった (`#V`)。出力は強さの順に良くならず、仕組みは確かめていない。3 は両方で良かった
  - 既定を 3 にした版を両モジュールに書き込み、両方を四角いモバイルバッテリー (TE-0012、2000mAh、PD 非対応) で動かして、`#G60` と `#p` を約 70 秒おきに送った。10 分間 (9 回) 6 面とも崩れず、両モジュールとも毎回 ACK と ping が返った (2026-11-03 14:35〜14:45、崩れないのは本人の目視)。電圧の低下は崩れの原因ではなかった (本人:「電圧低下は冤罪でした」)
- 辺のつながりから面と回転を出す計算: 面の画像の辺の中点を `+proj=qsc` の逆変換で球の上の点にし、接する辺同士の点が一致する組み合わせを全部試す。モジュール 1 の実際の割り当てを再現し、モジュール 2 では 1 通りだけが合った
- 枠のコーナージョイント (`hardware/frame/joint.stl`、透明な樹脂) が届き、8 個の頂点で 6 枚の LCD をくわえて立方体に組めた。前より「かなり良くなった」(本人、写真 gyazo e0a1d338、b6cd71d0、2026-11-05)。まだ一部の頂点はマスキングテープで留めている
- 1 年モード: MODIS Aqua の昼の地表の温度の半月平年値 (2012-2021、JAXA Earth の STAC) を 24 コマにし (`host/lst_year.py`)、microSD のシーン 101〜124 に各モジュール 3 面ずつ書いた。中継から `host/play_scenes.py` で 5 秒ごとに切り替え、季節の移り変わりがよく見えた (本人の目視、2026-11-05)。横の 4 面それぞれ、1 年中陸のかからない海に情報窓 (時期・目盛り・出典) を置いた
- 北極側の Sense の microSD は書き込み中に抜けることがある: 2026-11-05、USB を挿し直したあとの書き込みの途中から `w error: cannot open` になり、直前に書いた 7 面分が消えた (前からあったファイルは残った)。挿し直すと `#C` は通り、書き直して直った
- 名前つきのシーンと `#v` (a5cceec): しきさい (GCOM-C SGLI) の昼の地表の温度の半月ごとの実データ 2025-01-01〜2026-10-01 の 43 コマを `host/lst_year.py --set shikisai-lst` で作り、`send_scene.py --tree` で両モジュールの `/scenes/shikisai-lst/<日付>/` に 3 面ずつ書いた (1 モジュール約 5 分、計 59MB)。`#vshikisai-lst,2025-07-01` で 1 コマ、`#vshikisai-lst,2025-01,2025-01,1` でループし、次の命令で止まった (2026-11-05)
- 四角いモバイルバッテリー (TE-0012) 2 個を満充電にして 16:38 ごろ電源を入れ、`battery_watch.py --loads tGvj` (`#t`、`#G`、`#v`、`#j` をランダムに 1 分ごと) で測ると、南極側は 17:25:45〜17:26:30 に、北極側は 17:36:31〜17:36:45 に止まった。持ち時間は約 47 分と約 58 分 (2026-11-05、`~/logs/cube-battery-20261105.csv`)。10/29 の `#G` だけ (出力 1) の約 1 時間 29 分より短い。北極側の ping は 50 周中 18 周しか届かなかった (ACK は毎回返った)。理由は未確認
- TE-0012 はパススルー給電ができる。電池が切れた 2 個を USB-C の電源につないで充電しながら、バックライトを消して (`#b0`) 一晩置いた。翌朝 `#b1` を送ると両モジュールとも ACK が返り、バックライトが点いた (2026-11-05 夜〜11-06 朝、点いたのは本人の目視)。十分な出力の USB-C 電源につないでバックライトを消しておけば、一晩動き続ける
- 南極側モジュール 1 個の消費を USB チェッカーで見ると、起動して絵を出した状態で 5V 0.8A、`#b0` でバックライトを消すと 5V 0.4A (2026-11-06、本人の読み)。バックライト 3 枚でおよそ 2W、残りの 2W は XIAO (ESP-NOW の取りこぼしを防ぐため `WiFi.setSleep(false)` で無線を眠らせていない)、LT7680 3 個、液晶 3 枚の分。TE-0012 (2000mAh、約 7.4Wh) なら、点灯で約 1.5 時間、消灯で約 3 時間の計算になり、10/29 の約 1 時間 29 分と合う
- 残りの 0.4A を `#z` (lt7680_multi/README.md) で 1 つずつ止めて、南極側を pi4-deck の USB 給電で測った (USB チェッカー、本人の読み)。バックライト消灯 0.40A、無線の省電力を足して 0.38A、CPU 80MHz を足して 0.37A、液晶 3 枚のスリープを足して 0.29〜0.30A、LT7680 3 個の sleep を足して 0.13A。いちばん大きいのは LT7680 (0.17A)、次が液晶 (約 0.08A) で、XIAO の無線と CPU は合わせて 0.03A。`#zl0`、`#zp0`、`#b1` で起こすと、3 面とも眠らせる前の絵が戻った (2026-11-06)。`#zl1` のあと STSR の省電力ビットが立ったのは基板 0 だけで (0x56、ほかは 0x54)、それでも 3 個とも電流は下がった。無線の省電力のまま ESP-NOW の命令が届くかは、まだ確かめていない

- ビルド: `arduino-cli compile --fqbn esp32:esp32:XIAO_ESP32S3` (esp32 コア 3.3.12)
- 書き込み: pi5-deck に USB 接続し、esptool 5.3.1 で `--before usb-reset --after hard-reset write-flash 0x10000 <app.bin>`
- シリアル命令は `#` を先頭に付けた 1 文字 (`#E` 地球、`#K`/`#W` 黒/白で塗る、`#0` 初期化の流れを 1 回、`#r` 状態)。端末側は `stty raw -echo` にしないと XIAO の出力が命令として戻る
- 映っているかの判定は Web カメラで、白で塗った写真のパネル領域の明るさ (映っていれば 220 以上、黒や固まった画面は 150 以下) で行った。1 枚の色だけでは固まった画面と正常を取り違える

## 起動時にパネルが映るか

2026-10-16 夜、D2 と CON1 16 番 (LCD_CS) の間の線がつながっていないことが分かった。つなぐと、USB-C の電源投入でパネルが安定して映るようになった (lt7680_multi の既定ビルド、流れ 2 回で 5/5、本人の目視)。メーカー推奨どおりの最小の起動 (試験時の旗 `BOOT_MINIMAL`、今は既定で旗は無い: 電源投入から 30ms 待ち → LT7680 の初期化 → ST7701S の初期化 1 回 → 表示オン) でも映る (カメラ判定 3/3、抜いていた時間 2.2〜4.7 秒、本人の目視でも全回)。画素 20MHz と組み合わせて 4/4 (本人の目視)。2026-10-16 夜からこれが `lt7680_multi` の既定の起動 (電源投入から地球まで約 1 秒)。LCD_CS がつながっていないと、パネルの 3 線 SPI の CS は浮いたままになる。

いつから外れていたかは分かっていない。下の表と、それをもとにした「流れを 2 回行う」などの手順は、LCD_CS が浮いていた可能性がある時期の数字なので、つないだ状態で測り直すまでは根拠にしない。

### LCD_CS が浮いていた可能性がある時期の数字 (参考)

「流れ」= LT7680 のハードリセット → PLL/SDRAM → 表示オン → 塗りつぶし → パネルの SWRESET + 初期化列 ×2。

| 起動の種類 | 起動時の流れ | 結果 |
|---|---|---|
| XIAO だけのリセット (esptool、esp_restart) | 1 回 | 0/8 |
| XIAO だけのリセット (esptool) | 2 回 | 10/10 |
| USB-C の電源投入 | 2 回 | 0/3 (本人の目視) |
| USB-C の電源投入 | 1 回 | 0/3 (本人の目視) |
| USB-C の電源投入 | 0、5、10、20、40、80 秒に 1 回ずつ (診断版) | 最初の流れの直後だけ白が映り、5 秒目の流れ以降は黒 (カメラ、1 回) |

- 映っていない状態から、動作中にシリアル命令 `#0` (流れ 1 回) を送ると映る (直近 4/4)
- XIAO だけをリセットし、パネルに触らなければ表示は保たれる (10/10)
- 電源投入で毎回映る起動の流れは、まだ見つかっていない。機構も未解明
